# 国内高延迟下的首屏请求审计(2026-08-06)

实测网络地板:平均 79-99ms,最差节点 200-305ms(上海电信 271 / 重庆联通 305 / 汕尾联通 242)。
这是境外部署的物理下限,代码改不动。能改的只有**往返次数**——每省一次往返 = 省 100-300ms。

⚠️ 一个必须先讲清的事实:**静态资源和数据请求走的不是同一条链路**。

| 链路 | 目的地 | 说明 |
|---|---|---|
| 站点 HTML / JS / CSS | Vercel 边缘(实测 `X-Vercel-Id: sfo1`,`Age: 38946` = 边缘缓存生效) | 打到最近 PoP,不回源 |
| 音频 mp3 | `audio.bigmooneducation.com`(Cloudflare) | 实测 `public, max-age=31536000, immutable` ✅ |
| 插图 jpg | Supabase Storage(Cloudflare 前置) | 见下方"仍有 501 张只缓存 1 小时" |
| **所有数据库请求** | **Supabase us-east-1(弗吉尼亚)** | **不经任何 CDN,每次都是跨太平洋往返** |

所以 79-99ms 是静态资源的数字;**每一次 `supabase.from()` 的实际成本远高于此**。
压请求数的重点在数据请求,不在静态。

## 一、资源与 CDN 核查结果

### 1.1 🔴 已修:hashed 资源被强制每次回验(改动已提交,下次部署生效)

实测:

```
GET /assets/index-Cc5nROxV.js
Cache-Control: public, max-age=0, must-revalidate   ← 错
X-Vercel-Cache: HIT

带真 ETag 重取 → HTTP 304
```

`/assets/*` 的文件名自带内容 hash(内容变 → 文件名变),本该 `immutable`。
现在是 `max-age=0, must-revalidate`,意味着**每次访问、每个 chunk 都要发一次条件请求**。
首屏约 10-15 个 chunk × 200-300ms,即使全部 304 也要白白等一轮。

已在 `vercel.json` 加 `headers`:`/assets/*` → `max-age=31536000, immutable`;
`public/` 里无 hash 的图片/视频 → `max-age=86400, stale-while-revalidate=604800`
(`spark-hero.mp4` 1.1MB、`library-hall.jpg` 356KB、`og-cover.jpg` 130KB 之前都在每次回验)。

**这是本次投入产出比最高的一条,且零代码风险。**

### 1.2 ✅ 音频:已正确走 CDN 边缘

`audio.bigmooneducation.com`(Cloudflare)返回 `public, max-age=31536000, immutable`。
`speak.ts` 先猜 CDN URL、命中就完全跳过 Edge Function —— 这套设计是对的,保持。

### 1.3 🟡 Supabase Storage 两处头没配对

现查 `storage.objects`:

| 桶 | 对象数 | cacheControl | 问题 |
|---|---|---|---|
| `tts-audio` | 53,787 | `max-age=public, max-age=31536000, immutable` | **格式非法**:`max-age=public` 不是合法值 |
| `library-illustrations` | 968 | `public, max-age=31536000` | ✅ 正确 |
| `library-illustrations` | 501 | `max-age=3600` | 只缓存 1 小时,超时就跨境重取 |
| `library-illustrations` | 1 | `no-cache` | 每次都回源 |
| `textbooks` 等 | 6 | `max-age=3600` | PDF,影响小 |

`tts-audio` 那条非法头的成因:`supabase/functions/tts/index.ts` 把**整串 header** 传给了
`cacheControl` 选项,而 Supabase 只接受秒数、自己拼 `max-age=`,于是拼成了 `max-age=public, ...`。
走 `audio.bigmooneducation.com` 时被 Cloudflare 规则覆盖所以没暴雷,但**回退到裸 Supabase URL 的路径会中招**
(`speak.ts:78` 的 fallback)。已改源头为秒数;存量 5.4 万条要靠 SQL 刷元数据(见 `SQLAA/storage_cache_control_fix.sql`)。

> 测量陷阱备忘:对 Supabase Storage 用 `curl -I`(HEAD)会返回 `no-cache`,那是它的 HEAD 实现问题,
> 不是真实缓存策略。必须用 GET(`curl -r 0-0`)才能看到真实头。

### 1.4 🟡 apex → www 多一跳

`https://bigmoonenglish.com/` → `307` → `https://www.bigmoonenglish.com/`。
直接输域名的用户白付一次完整往返。在边缘完成,成本是一个 RTT,不是回源。
要消掉需要把 www 设为非重定向的主域或在 DNS 层处理 —— 收益 1 个 RTT,自行权衡。

## 二、首屏请求数清单

计数口径:**组件挂载后、首屏可用前发出的跨境请求数**。
`auth.getSession()` 读 localStorage,**不计**(0 往返);
`auth.getUser()` 每次都发 `GET /auth/v1/user`,**计 1 往返**
(证据:`node_modules/@supabase/auth-js/.../GoTrueClient.js:2489-2503`,无 jwt 参数分支照样走 `_request`)。

### 2.0 全局税:每个页面都要先交

| 组件 | 请求 | 备注 |
|---|---|---|
| `MistakeReviewGate` | `auth.getUser()` + `user_mistakes` 查询 | 每页 1-2 次;已登录且当天未做过复习门时是 2 |
| `useActiveHeartbeat` | `auth.getUser()` + `learning_heartbeats` insert | 周期性,不算首屏,但每个 tick 2 次往返 |
| `UserAvatarMenu` | `auth.getSession()` | 0 ✅ |

**合并方案(优先级最高,一次改动全站受益):**
全站 176 处 `auth.getUser()` vs 31 处 `auth.getSession()`。绝大多数只是为了拿 `user.id` 去拼查询条件 ——
这种场景用 `getSession()` 从本地读即可,**安全性不受影响**(数据边界由 RLS 在服务端保证,客户端 uid 只是过滤条件)。
建议加一个 `getUserIdFast()` helper 统一替换。按每页省 1-2 次往返算,全站每次导航省 200-600ms。

### 🔴 首页 `/` —— 2 个请求 100% 浪费

`Index.tsx` 的两个 effect 会发:
1. `profiles.select("onboarded_at")` —— 只喂给 `needsOnboarding`
2. `useStreakStats` → `rpc get_user_streak_stats`

但 `Index.tsx:76` 是 `if (!forceHub) return <LandingPage />;` —— **默认所有人(含登录用户)都渲染 LandingPage**,
上面两份数据一个都用不到。Hook 在 early return 之前执行,所以照发不误。

**合并方案:** 把这两个 effect / hook 移进只有 `?hub=1` 才渲染的那个分支(或直接放进子组件)。
**省 2 次往返,零功能变化。** 这是全站访问量最大的页面,建议第一个改。

---

### 🔴 `/library` 书架 —— 6 请求 / 3 波

```
波1: getLibrarySegment()      (2 查询)
   ∥ listBooks()              (1 查询,library_books)
   ∥ getBookVisibility()      (1 查询,library_books ← 同一张表!)
波2: currentUserId()          (1 次 auth.getUser 网络往返)
波3: fetchProgressMap(uid,…)  (1 查询)
```

**合并方案:**
1. `listBooks` 与 `getBookVisibility` **查的是同一张 `library_books`**,只是列不同。把 `visibility` 并进
   `LIST_COLS`,删掉 `getBookVisibility()` 这次请求。**省 1 次。**
2. `currentUserId()` 改用 session 本地读 → **波2 整个消失**,`fetchProgressMap` 可以并进波1。**省 1 次往返 + 1 个波次。**
3. 剩下的 segment / books / progress 三查可包成一个 RPC(`get_library_shelf(uid)`)一次拿回。**省 2 次。**

改完:**6 请求 3 波 → 1-3 请求 1 波**。按 280ms/波算,首屏快 ~560ms。

---

### 🔴 `/library/:key/read` 阅读器 —— 11 请求 / 5 波(最重)

`LibraryReader.tsx:162-241`:

```
波1: getBookByKey                                     1
波2: Promise.all[ currentUserId(网络), listFavoritedTerms,
                  getBookCultureNotes, listBookmarks,
                  getBookWordSenses ]                 5
波3: hydrateFromCloud(uid, bookId)                    1
波4: getChapterOfSeq(bookId, last_seq)                1
波5: Promise.all[ getChapterSentences,
                  getChapterIllustrations,
                  getChapterChunkTerms ]              3
```

5 个串行波次 × 280ms ≈ **1.4 秒纯排队**,还没算每个请求自身的传输时间。

**合并方案:**
1. `currentUserId()` 换本地 session → 波2 不再被网络 auth 拖住,且 `hydrateFromCloud` 可提前进波2。**省 1 往返 + 1 波。**
2. 波3+波4 合一:`hydrateFromCloud` 返回 `last_seq` 后才能算章号 —— 让 RPC 直接返回
   `{state, initial_chapter}`,服务端一次算完。**省 1 波。**
3. 终局:做一个 `get_reader_bootstrap(book_key, uid, ch?)` RPC,把书目 + 断点 + 初始章 + 该章句子 +
   插图 + 语块 + 书签 + 收藏词 + 按书词义**一次返回**。**11 请求 5 波 → 1 请求 1 波,省约 1.1-1.4 秒。**
   这是全站单页收益最大的一处。

---

### 🔴 `/dashboard` —— 11 请求 / 3 波

```
波1: auth.getUser()                                   1(网络)
波2: mastery_with_proportions                         1
   ∥ useStreakStats → rpc get_user_streak_stats       1
   ∥ useDashboardExtras 的 Promise.all                8
波3: enrichMasteryGpsData                             0 查询(纯计算,已确认)
```

**合并方案:**
1. `getUser` → session 本地读,**波1 消失**,后面全部可以立刻并发。**省 1 往返 + 1 波。**
2. `useDashboardExtras` 那 8 个并行查询里有一个是 `pet_state` —— **宠物板块已全站下线**,
   这是死查询,直接删。**省 1 次。**
3. 8 查 + streak + mastery 共 10 个只读聚合,包成一个 `get_dashboard_bootstrap(uid)` RPC。
   **11 → 1**,首屏从 3 波变 1 波。
