# 生产库 SQL 交付

前提:**我从不写库**。所有 SQL 由 Aaron 在 Supabase SQL Editor 手动执行。
我只出文件 + 出证据。SQL 一律进 `SQLAA/`,并给 GitHub 完整 URL(不给相对路径)。

## 一、SQL 的形状

每份都是**完整事务 + 幂等 + 自带断言**:

```sql
BEGIN;
SELECT 'BEFORE' AS stage, <关键读数>;
-- …UPDATE / INSERT…
SELECT 'AFTER'  AS stage, <关键读数>;

DO $gate$
DECLARE n int;
BEGIN
  -- 每条断言不过就 RAISE EXCEPTION,整笔回滚。不靠人眼看一列 t/f。
END $gate$;
COMMIT;
```

- 幂等:`ON CONFLICT (…) DO UPDATE`;改名用 `WHERE id = … AND lower(headword) IN (旧, 新)`。
- 分片:走**同一个 emitter** 的 `--shards=N`,**绝不另写切分脚本**
  (手搓第二个生成器 = 2026-08-09 那次 0-based sort_order 事故)。
- 一次性修复文件名要和整批灌库**分开**(`vocab_fix_<word>.sql`),否则待跑清单分不出哪份是什么。

## 二、断言的两条铁律

**① 判据锁在本批,绝不写全表。**
`(SELECT count(*) FROM t WHERE col IS NOT NULL) = 本片行数` 在分片下**必然为 f** ——
那反映的是"别的片还没跑",不是本片出错。用临时表复用同一份 VALUES:

```sql
CREATE TEMP TABLE _batch(id uuid PRIMARY KEY, val text) ON COMMIT DROP;
INSERT INTO _batch VALUES (…);
UPDATE t SET col = b.val FROM _batch b WHERE t.id = b.id;
-- 断言只 JOIN _batch,不扫全表;全表读数只作参考,明写"不作判据"
```

**② 判据引用的表/常量必须真能匹配到行,否则先绿的是断言自己。**
踩过:`JOIN vocab_banks b ON b.code = 'all'` —— 根本没有 `code='all'` 这个库,
join 不到行 → `NOT EXISTS` 恒真 → **两条完整性断言永远绿,等于没写**。
错判成 `f` 顶多虚惊,恒 `t` 是真的放坏数据过去。

## 三、必查清单(按操作类型)

**改 headword**(半截搭配、错拼):
- 原地改、**保留原 id**。新建行会与 `vocab_word_banks` 断开挂载 ——
  词还在,但从所有词库里消失,而在 `vocab_words` 单表上完全看不出来。
- 断言必带:① 改名生效 ② `count(*) FROM vocab_word_banks WHERE word_id=<id>` ≠ 0
  ③ **同名唯一性**:`count(*) WHERE lower(headword)=<新名>` 必须正好 1
  (库里本来就有同名词条时会两条并存,都能查都能学,用户看到哪条全看排序,表面完全正常)。
- 一次性修复**全程按 id 锁定**,不走 `lower(headword)`、不加 `def_zh IS NULL`。

**🔴 不为改一个词开通用覆盖通道。** 内容 SQL 里 `AND def_zh IS NULL` 那道护栏是
14,776 个词不被静默覆盖的唯一屏障;做成开关后每次流水线跑都能盖掉人工内容且无迹可寻。
按 id 锁定就能把作用面钉死在一行,护栏不用动。

**回填音频**(内容寻址 `https://audio.bigmooneducation.com/<2位>/<64位sha256>.mp3`):
- 形态正则:`^https://audio\.bigmooneducation\.com/[0-9a-f]{2}/[0-9a-f]{64}\.mp3$`
- 前缀自洽:`substring(url from 36 for 2) = substring(url from 39 for 2)`
- **重烧后新旧 URL 必须不同** —— 文件名是文本内容的哈希,文本没换成功新旧就一模一样。
  形态检查放行、数量检查放行,**只有直接比对新旧才当场识破"改了个寂寞"**。
- 合成参数定版:`openai | alloy | speed=1 | accent 空`。差一个字符就分叉出重复文件,
  前端 `predictCdnUrl` 会指向另一个。

**批量传输**:
- **count 对 ≠ 值对**。30,915 条里坏过 2 条:一条哈希少 2 位(形态正则抓到),
  另一条**等长替换**——长度对、形态对、前缀自洽,所有形状检查全部放行。
  唯一能抓的是**逐条比对值**:源数据装临时表 → 报 `mismatched_before` → 就地改正
  → `DO $gate$` 复查,仍不一致就 `RAISE EXCEPTION` 整笔回滚。
- 等长替换的后果是"前端点了没声音、后台一切正常"的幽灵 bug。
- 批次抽样探针:每批取首/中/末三行回查,一条 SQL 就能定位哪些批次没落库。

**执行前预检**:SQL 里用到的列(如 `pos`)先确认存在,否则整笔回滚白跑。
无 id 护栏的 `lower(headword)` 更新,执行前先查有没有同名行。

### 硬编码清单必须与实时判据做 md5 逐条比对(不是比行数)

SQL 里那几百上千行 `VALUES` 是**出件时刻**的快照。交付前必须证明它与
**此刻按判据现算的集合**逐条相同 —— **只比行数、只比格式都不够**:
数量对、形态对、前缀自洽,而其中一条 UUID 被换成了另一条,所有形状类判据全部放行。

> 本项目被这类错误咬过:30,915 条音频里坏了 2 条,其中一条是**等长替换** ——
> 长度对、正则对、目录前缀自洽,唯一能抓的是逐条比对值。

做法(两边各取 md5,必须相同):

```js
// 本地:把 (键, 值) 对**排序后**拼接取 md5。排序是关键,否则两边顺序不同就白比。
import { createHash } from 'node:crypto';
const localMd5 = createHash('md5')
  .update(rows.map(r => `${r.key}|${r.value}`).sort().join('\n')).digest('hex');
```
```sql
-- 库里:同样的拼法,string_agg 走 ORDER BY 保证顺序一致
SELECT md5(string_agg(key || '|' || value, E'\n' ORDER BY key || '|' || value))
  FROM <按判据现算的集合>;
```
两个 md5 不等就**别出件**,先查为什么。把它做成出件脚本的一步,
不要靠"我核对过了" —— 这次清单碰巧完全正确,但那是**结果对,不是流程里有这道关**。

## 四、交付前必须做的验证

**用 pglite 真跑,别肉眼读。** 这机器上没有 psql、没有 docker:

```bash
npm i @electric-sql/pglite     # 纯 WASM,3 秒装完
```

`new PGlite()` 起内存 Postgres,`db.exec(sql)` 跑整份文件,
`BEGIN/COMMIT`、`CREATE TEMP TABLE … ON COMMIT DROP`、`DO $gate$ … RAISE EXCEPTION` 全支持。
建一套只含断言用到的列的最小表结构就够。

**必须做变异测试,不能只跑"好"数据:**
1. 原样 → **必须放行**(证明不误伤);
2. 跑第二遍 → **必须幂等**(行数不翻倍);
3. 逐个把数据弄坏 → **每一种都必须被拦**:
   少一行 / id 库里不存在 / 值写歪 / URL 空串或形态非法 / 枚举越界 /
   挂载事先就断 / 库里已存在同名词条 / 某条 UPDATE 被删掉。

⚠️ **拦下了不等于拦对了。** 有个用例一度是被**语法错误**(我删行时留了悬空逗号)拦下的,
断言根本没跑到 —— 看上去绿,实际完全没测到。看清是谁拦的。

⚠️ **「没拦下」也不等于「拦不住」。** 反过来的那一面,同样咬人:
两条变异显示"没被拦",我差点据此去加断言 —— 查了才发现**破坏语句被插在 `DO $gate$` 之后**,
断言早跑完了,闸门根本够不着。
**判一个闸门无效之前,先确认破坏发生在它的作用域内。**
变异要插在断言**之前**;插在 COMMIT 前(断言之后)的破坏,任何断言都拦不住,
那测的不是闸门,是"SQL 能不能在最后追加语句"。

### 断言判**终态**,不判"这一次改了多少"

`IF 减少量 <> 175 THEN RAISE EXCEPTION` 这种写法,**第二遍跑必炸**:
该删的已经没了,减少量是 0。而重跑一份已跑过的 SQL 本该是安全的 no-op。

比"不幂等"更糟的是**它会让人以为库出了问题** —— 报错信息长得像"数据对不上"。

做法:删除/更新**之前**先快照"本次真正会被影响的那些行",拿它当基准:

```sql
CREATE TEMP TABLE _cut_present AS
  SELECT … FROM _cut c JOIN <目标表> t ON …;   -- 删之前确实存在的那些
-- 断言:减少量 = (SELECT count(*) FROM _cut_present)
-- 第二遍跑时 _cut_present 为空 → 0 = 0 ✓,仍然能抓住多删/少删
```
配套的终态判据("该删的一条不剩""该有的值逐条一致")天然幂等,优先用它们。

## 五、验证工具本身也要被验证

### 标准动作:改判据 → 先喂已知答案的样本 → 确认它仍能点名

**这是每次改判据的第一步,不是事后想起来才做的抽查。**

1. 动判据**之前**,先备好至少一个**已知真阳性**(确定该被点名的)和一个**已知真阴性**
   (确定不该被点名的)。手头没有就先造一个 —— 造样本的成本远低于交付一批误报。
2. 每改一版,**立刻重跑这两个样本**:
   - 真阳性**没被点名** → 判据坏了,别看总数好不好看;
   - 真阴性**被点名** → 判据误伤,同样是坏了。
3. 只有两个都对,才去看总数、看分布、看短名单。
   **顺序反过来就完了** —— 总数"看着合理"是最容易骗过自己的信号。

反例(真事):第二版扫描器总数从 1371 降到 13,看上去判据一下子精准了,
实际是**真阳性掉进了弱档、13 个误报占着强档**。只看总数的话这版会被当成成功交付。

同族扫描器写了四版,前三版判据全错:

| 版本 | 判据 | 错在哪 |
|---|---|---|
| 1 | 对所有词性看"三条例句邻词固定" | 1371 条噪声 —— 抽象名词天然吃 `the X of`,那是能产的语法框架不是固定搭配。**选错了对象,不是阈值问题** |
| 2 | 标注后面的短语含不含词条本身 | **正好判反**:唯一真阳性掉进弱档,13 个误报占强档 |
| 3 | `split('\n')` 数义项 | ECDICT 的 `\n` 兼作换行续行,真阳性被算成 3 个义项又掉出去 |

三次都是靠**"已知真阳性有没有被点名"**才发现判据坏的。没有那个已知坏样本,
第二版那 13 个误报就当战果交付了 —— 全表看上去还挺像回事。

同理,写探针/对账脚本时:
- **先怀疑探针,再怀疑数据。**"全部不合格""五片合计 0 行"这类极端读数,九成是探针读错了
  (调用签名写错、屈折表传空、正则被 shell 多吃一层转义)。
- 正则一律写进 `.mjs` 文件跑,**别用 `node -e`** —— `\\(` 会被 shell 再吃一层,量出来是 0。
- 拿不到 ≠ 缺失。限流/超时是**第三态**,单独打印并排除,别混进"缺失"计数。

## 六、报告纪律

- **只信库里的读数,不信执行方的汇报。** 有一批 3,200 行汇报"全部成功、已验证写入",
  实际一条都没写进去,靠边界行回查才发现。一律独立做 BEFORE/AFTER 差值验证。
- 断言必附**当次实测**证据(覆盖率/计数/零重合),测不了就别断言。
- 证据要分清「Aaron 回报」和「库内实证」。
- 内容类改动(释义/例句/语块)造完**先贴出来给 Aaron 审**再落库;
  纯技术 UI / 脚本可直接 push。
- 改闸门必跑**全量回归**(`node scripts/vocab/regress-gates.mjs`,末行 `GATE_VERDICT`,
  别用管道取退出码 —— 取到的是 grep 的)。作废 ≠ 通过:有一个词没参与判定,这轮回归就不算数。
